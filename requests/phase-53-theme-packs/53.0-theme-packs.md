# Phase 53 — Theme Packs

## Why
Designed April 2026 (leonardoPrompts/portrait-prompts.md, now at
~/Desktop/LeonardoPrompts/Cascade/), parked since Phase 23 as
"[Theme Pack] — product feature, user-scheduled". Justin scheduled it
2026-09-04. A theme pack = full visual theme + matching prebuilt
assistant persona (name, portraits, personality), Delamain-in-Cyberpunk
being the prototype. All prerequisites shipped long ago: CSS var theme
system, `<Portrait/>` graceful fallback (22.1), configurable overseer
identity (lib/overseer-settings.ts). Portraits themselves still come
from Justin's Leonardo sessions; missing assets degrade to the SVG
placeholder by design, so the feature ships fully wired without them.

## Scope
1. **`lib/theme-registry.ts`** — the 12 packs from the design doc
   (sunny, cyberpunk, console, cog, sprite, margin, curator, sage,
   pilot, pixel, quiet, specter), each: key, label, description,
   4-swatch preview, persona {name, portraitIdle, portraitTalking,
   personality}. Cyberpunk keeps the existing Delamain assets; all
   others point at `/portraits/<key>/{idle,talking}.jpg`.
   `resolveThemeKey()` migrates legacy stored values ("dark"→cyberpunk,
   "light"→sunny, unknown→cyberpunk).
2. **`lib/theme-pack-apply.ts`** — `applyThemePack(key)` sets the
   theme AND the pack persona, but only overwrites persona fields when
   the current persona is pristine (factory defaults or exactly some
   pack's persona). A hand-customized assistant is never clobbered
   (`shouldApplyPersona()`).
3. **`app/components/theme-provider.tsx`** — Theme type widens to the
   12 registry keys; stored legacy values resolve through
   `resolveThemeKey`.
4. **`app/globals.css`** — a `[data-theme="<key>"]` var block per
   pack. `dark`/`light` selectors kept as aliases of cyberpunk/sunny
   (old localStorage values render correctly even before JS runs).
5. **`app/settings/page.tsx`** — theme cards generated from the
   registry (12 cards), click applies the pack via `applyThemePack`;
   card shows the persona name it bundles.
6. **`public/portraits/README.md`** — where Leonardo outputs land.

## Acceptance criteria → tests
- AC1 Registry has exactly the 12 design-doc packs, unique keys,
  complete fields; cyberpunk persona = Delamain with existing assets;
  every other pack's portraits under `/portraits/<key>/`.
  → `lib/theme-registry.test.ts`
- AC2 `resolveThemeKey`: "dark"→"cyberpunk", "light"→"sunny", every
  registry key→itself, null/garbage→"cyberpunk".
  → `lib/theme-registry.test.ts`
- AC3 `shouldApplyPersona` true for factory defaults and for any
  pack persona verbatim; false once name or either portrait is
  customized. `applyThemePack` persists theme + persona (pristine) /
  theme only (customized), and sets data-theme on <html>.
  → `lib/theme-pack-apply.test.ts` (jsdom)
- AC4 globals.css contains a var block for all 12 keys, each
  defining the full token set (bg/panel/border/status/text/scanline/
  glass vars); `dark` and `light` alias selectors survive.
  → `lib/theme-css.test.ts` (reads the CSS — drift guard)
- AC5 ThemeProvider hydrates a legacy "dark"/"light" localStorage
  value into the migrated key. → `app/components/theme-provider.test.tsx` (jsdom)
- AC6 Settings theme grid renders from the registry (12 cards, one
  ACTIVE) — covered structurally by AC1+AC5 plus lint/tsc; the page
  itself stays a thin map over `THEME_PACKS` (tests-after escape not
  needed: no new logic lives in the page).

## Out of scope
- Generated portraits (Justin's Leonardo session; `<Portrait/>`
  fallback covers absence).
- Per-theme voices, per-project personas (not in the design doc —
  flagged as an open question 2026-09-04, unanswered).
- Hosted per-user persistence of theme/persona (localStorage today;
  revisit when hosted accounts grow settings).
