# 53.4 — Per-project personas

## Why
Justin's standing "get every feature in" mandate; the open design question
is resolved with the hosted-first call: the persona override lives on the
**Project row** (`themeKey String?`), not localStorage — it syncs through
Postgres, works hosted, and every client sees the same assistant for a
project. `null` = inherit the global assistant.

## Scope
1. Prisma: `Project.themeKey String?` (+ db push, references/schema.md).
2. `lib/persona-prompt.ts` gains `projectPersonaBlock(themeKey)` — pack
   lookup + buildPersonaBlock; "" for null/unknown keys.
3. PATCH `/api/projects/[slug]`: `themeKey` joins the allowlist, validated
   against the registry keys, explicit `null` clears it.
4. Project chat route appends `projectPersonaBlock(project.themeKey)` to
   the built system prompt (after the cached block — see route comment).
5. Project page: "Assistant" selector (pack dropdown + None/inherit) that
   PATCHes themeKey; shows the pack portrait.

## Acceptance criteria → tests
- AC1 PATCH persists a valid key, rejects garbage (400 when it's the only
  field), and null clears → app/api/projects/[slug]/route.themekey.test.ts
- AC2 projectPersonaBlock: valid key → block with that pack's name +
  personality; null/unknown → "" → lib/persona-prompt.test.ts
- AC3 chat wiring + selector are thin (tsc/lint + existing suites).
